    STM32MP135F-DK MicroPython/LVGL target¶

    This is a personal project by Nunzio Raciti and is not affiliated with or endorsed by STMicroelectronics.

    Target: STM32MP135F-DK, MB1635, running MicroPython with LVGL and controlled by LVGL MPY Studio. The ST-LINK virtual COM port remains the Linux console and is never reused as the MicroPython REPL.

    Current status¶

    • Phase 0 reconnaissance: complete; see docs/ricognizione.md.
    • Phase 1 flash and initial inventory: complete.
    • Phase 2 system preparation: complete.
    • Phase 3 Cortex-A7 MicroPython/LVGL cross-build: complete.
    • Phase 4 MCU-style REPL: Linux HIL tests, performance, stress and reboot validation complete.
    • Phase 5 DRM display, Goodix touch and LVGL MPY Studio demo: complete, including rendering performance and repeated soft-reset resource checks.
    • The physical B1 safe-mode check passes; the Windows HIL checkpoint remains open.
    • Phase 6 LVGL MPY Studio: the Studio imports the board definition in studio-board/ from a file.
    • Phase 7 start-up and robustness: ready screen, REPL independent of the display, systemd watchdog on the REPL hub, journal in RAM; the 10 power cycles by hand remain.
    • Phase 8 packaging: scripts/deploy.sh, linux/install.sh and linux/uninstall.sh, checked with a full uninstall, reboot, install and reboot cycle.
    • Later phases: not started.

    Phase 1 verified configuration¶

    The microSD was flashed through CN7/USB_OTG with STM32CubeProgrammer 2.23.0 and the default OP-TEE layout FlashLayout_sdcard_stm32mp135f-dk-optee.tsv. STM32CubeProgrammer reported Flashing service completed successfully. The board then booted from microSD and showed the Weston/GTK demonstration on its panel.

    The inventory was collected through the ST-LINK console on host /dev/ttyACM0 at 115200 8N1. The captured command output, with serial CR/LF line endings normalized to LF, is in docs/log/stm32mp135f-dk-phase1-inventory.txt.

    Consequences for subsequent phases:

    • Phase 5 must implement a DRM dumb-buffer backend; fbdev cannot be assumed.
    • Touch discovery must use the Goodix device name or stable by-path identity, not a hard-coded event number.
    • Phase 2 must characterize the touch axes, backlight behavior and boot timing before changing services.
    • The existing USB network gadget must be inspected and extended with ACM in Phase 4, not replaced.
    • Weston and its graphical session are still enabled. No service, network setting, password or boot configuration was changed during Phase 1.

    Phase 2 configuration and installation notes¶

    These are the approved board changes to preserve when creating the final user installation guide and installer. They are not yet a complete installation procedure.

    Network and SSH¶

    • CN7/USB_OTG provides the existing NCM interface usb0; no gadget replacement is required.
    • The board has 192.168.7.1/24 and runs a DHCP server on this interface. The development host received 192.168.7.58/24; this host address is dynamic and must not be hard-coded.
    • SSH is provided by dropbear.socket, not OpenSSH. The key-only configuration was verified after a reboot; an attempt without the public key was rejected.
    • Root's actual home is /home/root, not /root. The authorized key must therefore be installed as /home/root/.ssh/authorized_keys, with mode 0600 and parent directory mode 0700.
    • The selected host public key is id_rsa.pub, fingerprint SHA256:Qak5m6jc+Adn/q9ouKuO/q9Yd2lnJzq4f0c9ocACwrU.
    • /etc/default/dropbear contains DROPBEAR_EXTRA_ARGS=" -s" to disable SSH password authentication. The local root password was not changed.
    • /etc/hosts maps 127.0.1.1 to mp135-mpy.

    Services and hostname¶

    The following units were explicitly approved and disabled:

    systemctl disable --now weston-graphical-session.service weston-checkgpu.service seatd-weston.service
systemctl disable st-hostname.service
hostnamectl set-hostname mp135-mpy

    st-hostname.service must remain disabled for this configuration: its original /usr/bin/st-hostname.sh script appends the end0 MAC suffix to a hostname on every boot. The script itself was not modified. All other services, including networking, Dropbear and the USB gadget, remain enabled.

    After the first reboot, all three Weston units were disabled and inactive, no systemd units were failed, and Nunzio confirmed a black panel with no ST demo. SSH remained available. A static OpenSTLinux boot logo can remain visible on later boots; without Weston it has no touch handling and is not an interactive application.

    Phase 3 cross-build and on-board validation¶

    The x86-64 Developer Package SDK archive SDK-x86_64-stm32mp1-openstlinux-6.6-yocto-scarthgap-mpu-v26.06.10.tar.gz was extracted and its installer completed successfully. The installed environment reports GCC 13.4.0, ARCH=arm, CROSS_COMPILE=arm-ostl-linux-gnueabi- and the expected OECORE_SDK_VERSION.

    The SDK and board both provide libffi 3.4.6, so MICROPY_PY_FFI=1 is retained. They also provide libdrm 2.4.120 and SDL2 2.30.1, but the final MicroPython binaries do not link SDL. The SDK environment does not export SIZE; the build script therefore sets SIZE, STRIP and READELF explicitly with the cross-tool prefix.

    Reproducible builds use scripts/build_mp135.sh. It builds mpy-cross for the host before loading the SDK environment and pins MicroPython v1.29.0, lvgl-micropython 58d18ce and lvgl-bindings 7740c2f (LVGL 9.5.0). The validated commands in this development workspace are:

    cd /opt/devel/lvgl/lvgl-mpy-linux
scripts/build_mp135.sh minimal
scripts/build_mp135.sh lvgl

    WORK_DIR defaults to work/ inside this repository and can be set to another workspace; SDK_DIR defaults to the matching SDK directory below it. Outputs and SHA-256 files are written to dist/.

    Build text data bss Total

    Both are stripped ARM EABI5 32-bit executables using /lib/ld-linux-armhf.so.3. The Phase 3 dynamic NEEDED entries were libm.so.6, libffi.so.8 and libc.so.6; Phase 5 adds libdrm.so.2 to the LVGL build for the DRM panel backend.

    On the board, the LVGL binary reports MicroPython 1.29.0, sys.platform=linux, build STM32MP135F_DK and LVGL 9.5.0. The existing PyDevices fake-display smoke test, tests/hil/t02_lvgl_smoke.py, passes twice including after lv.deinit(); the second scene renders successfully and the MicroPython heap returns to its initial value.     PyDevices reports that this build does not include the optional jpegio module: JPEG images will not draw, while PNG and LVGL BIN remain available. JPEG support was not required for this phase.

    Phase 4 MCU-style REPL¶

    The ST-LINK virtual COM port remains the Linux console. MicroPython uses the CDC-ACM function added to the existing USB gadget, preserving NCM networking, DHCP and SSH. On the validated host the gadget is /dev/ttyACM2, but the number is dynamic; the ST-LINK console must not be selected. The board-side device is /dev/ttyGS0. The REPL filesystem root is /usr/local/mpy/fs.

    The composite gadget requires the TX FIFO layout supplied by linux/stm32mp135f-dk-usb-composite.dtso. scripts/build_mp135_usb.sh verifies the exact original DTB hash, applies the overlay and validates the resulting layout. Do not rebind the gadget while it is active: install the DTB and reboot. The original and modified DTB SHA-256 values are respectively bf08a8e8aa6e0e2aacb1e37d76e1045c4702aff2239b8ff32234369b7235c294 and 1f8a0bdafc669ee05ca19c3fda920df197a1503ca4471b5d4a305bc99884d939.

    The board-specific mpyrepl user C module calls the upstream friendly/raw REPL implementations, executes boot.py and main.py, preserves the REPL mode and restarts in place with execve on soft reset. A linker wrapper around mp_hal_set_interrupt_char() enables terminal ISIG only while code runs. This is required for Ctrl-C in both normal raw REPL and raw-paste execution; no upstream MicroPython source is modified.

    tests/hil/test_repl.sh automates the serial checks, the real main.py crash and TCP smoke tests. It temporarily replaces :main.py and removes it on completion or failure; back up any user application before running it. Example:

    P=/dev/ttyACM2 TCP=socket://192.168.7.1:8266 tests/hil/test_repl.sh

    Set MPREMOTE and PYTHON if they are not on PATH. Set TCP= to skip TCP. For Git Bash on Windows, use P=COM<n>; fixture paths are converted with cygpath. The Windows checkpoint has not yet been run.

    Test Result

    A standalone mpremote mount . mounts the directory and then enters the interactive REPL, so it needs a terminal; a non-interactive shell should append a command such as exec as shown above.

    While code runs the CDC-ACM terminal has ISIG on for Ctrl-C only: Ctrl-Z and Ctrl-\ are disabled, both by the service stty and by mpyrepl, so they cannot stop or kill the REPL process. StartLimitIntervalSec=0 keeps Restart=always working through a crash loop.

    mpy-repl.service runs mpy-repl-hub (tools/mpy-repl-hub/): one MicroPython process on a pseudo-terminal, shared by the CDC-ACM port and one TCP client on 192.168.7.1:8266. The terminal's line discipline turns Ctrl-C into SIGINT for both channels. Output goes to both clients, as with MicroPython's dupterm on the MCU ports, and input from both reaches the REPL; a new TCP connection replaces the previous one. A client that stops reading for 1 s has its output dropped until it reads again, so a closed serial port never blocks the REPL. When MicroPython exits the hub starts it again. The TCP listener has no authentication or encryption and is bound only to the USB gadget address. Results: docs/log/stm32mp135f-dk-repl-hub.txt.

    UM2993 maps B1/USER1 to PA14 and B2/USER2 to PA13. The original configuration exposed PA13 as BTN_1 and drove PA14 as the blue heartbeat LED, so B1 presses produced no input events. The DTB overlay now disables that LED, exposes B1/PA14 as BTN_1 (0x101) and preserves B2/PA13 as BTN_2 (0x102) through /dev/input/by-path/platform-gpio-keys-event. Three complete physical B1 press/release cycles were observed. Holding B1 during an mpy-repl.service restart printed Safe mode: main.py skipped and prevented the temporary main.py marker from running; the normal restart control executed it. B2's mechanical switch on the validation board was damaged by a knock and is to be replaced; B2 was not tested.

    Logs are saved as docs/log/stm32mp135f-dk-phase4-hil.txt, docs/log/stm32mp135f-dk-phase4-performance.txt, docs/log/stm32mp135f-dk-phase4-stress.txt, docs/log/stm32mp135f-dk-phase4-reboot.txt and docs/log/stm32mp135f-dk-phase4-safe-mode.txt. See docs/stm32mp135f-dk-install.md for installation and recovery instructions.

    Phase 5 display, touch and Studio integration¶

    The panel is driven directly through DRM/KMS on /dev/dri/card0; this board has no /dev/fb0. The board-specific linuxfb user C module creates and maps a 480×272 RGB565 dumb buffer with a 1,024-byte stride, sets the DPI-1 CRTC and copies LVGL dirty rectangles into it. Weston and psplash-drm-start.service must be disabled so that MicroPython can become DRM master. The LVGL binary therefore has libdrm.so.2 as an additional dynamic dependency.

    python/linux/display_driver.py implements display-driver contract 1 with one 255 KiB full-screen buffer in DIRECT mode. Its service thread calls lv.timer_handler() every 5 ms, while the LVGL refresh timer is limited to 16 ms. The variant enables the MicroPython GIL (MICROPY_PY_THREAD_GIL := 1): the unix port has none by default, and without it the service thread and main.py or the REPL would call LVGL at the same time. With the GIL each LVGL call is atomic, as with the scheduled callbacks of the MCU ports; the full-screen animation measured 57.09 FPS (58.14 without the GIL). LVGL event handlers run in the service thread, so Ctrl-C does not stop a handler that never returns. stop() waits for the service thread to exit, preventing an immediate start() from creating overlapping service threads. Backlight control uses /sys/class/backlight/panel-backlight and defaults to 100%.

    python/linux/touch_evdev.py discovers Goodix Capacitive TouchScreen by name in /proc/bus/input/devices; the event number is not fixed. It polls the numeric file descriptor and decodes the verified 16-byte ARM32 input_event records with llHHi. ABS_MT_POSITION_X/Y, ABS_X/Y, tracking ID and BTN_TOUCH are handled. X increases rightward and Y downward, so no axis swap or inversion is needed. The board's FileIO does not expose read1() and its os module does not expose read(). After polling, each read therefore requests exactly one 16-byte event: the kernel supplies a complete event without MicroPython waiting to fill a larger buffer. Input is delivered one SYN_REPORT frame at a time and the LVGL continue_reading flag drains frames queued in the driver or kernel. A quick press and release therefore remain two distinct LVGL states instead of collapsing into a release with no click. tests/host/test_touch_evdev.py covers this quick-tap regression, partial frames, queued motion and the restricted FileIO method surface; tests/hil/t15_mp135_touch.py provides a visible click counter and callback timing on the panel.

    Both Python modules are frozen by the board manifest. The serial and TCP REPL services set MICROPYPATH=.frozen:/usr/local/mpy/fs:/usr/local/mpy/fs/lib; omitting .frozen makes display_driver unavailable to applications. On soft reset, mpyrepl closes inherited descriptors above stderr before execve, preventing DRM and input descriptors from accumulating across process restarts.

    shell-linux application¶

    examples/shell-linux extends the board with a separate Linux-capable shell without modifying the portable examples/shell application. It provides the MicroPython file and text commands, the edit and vi editors, and Linux executable lookup. Built-ins take precedence over Python programs in /usr/local/mpy/fs/bin, which in turn take precedence over executables in the Linux PATH; the linux command forces Linux execution.

    The board-specific linuxproc user C module starts each program with fork/execvp on a controlling PTY. It forwards serial keyboard input and terminal output, sets the 60x17 panel dimensions, handles non-blocking backpressure while continuing to drain output, and kills the whole process group if a MicroPython callback raises. MICROPY_PY_OS_DUPTERM is enabled for the shared panel/serial ANSI terminal. The terminal alternate screen saves character cells and redraws them on exit rather than duplicating the 255 KiB framebuffer, allowing both editors to run within the MicroPython heap.

    Installation, usage, limitations and HIL commands are documented in examples/shell-linux/README.md and linked from docs/stm32mp135f-dk-install.md. Autostart is optional and is not installed by default.

    Portable machine API decision¶

    The project will expose one MicroPython-compatible public machine API across Linux-only MPU boards and boards with a real-time MCU. User code should not change when the underlying hardware backend changes.

    • On STM32MP135F-DK and similar Linux-only boards, classes such as Pin, I2C, SPI, PWM, ADC and Timer will use kernel interfaces and drivers. Direct peripheral register access from Linux user space is not part of this design.
    • On MPU boards with a programmable MCU, an equivalent backend may communicate with MCU firmware through remoteproc and RPMsg/OpenAMP. Native MicroPython MCU ports should retain their existing machine API wherever possible.
    • Public method signatures, units, ranges, return values, exceptions and resource cleanup semantics should be shared across backends. Board-specific names, device discovery and capabilities must be kept out of application code.
    • Unsupported peripherals and operations must be reported explicitly rather than emulated silently. Board capabilities must be discoverable and documented.
    • API compatibility does not imply equivalent timing guarantees. Linux-only backends must not claim hard real-time behavior; future real-time control-loop offload requires a separate, explicitly defined API.
    • The different backends should run the same hardware-in-the-loop contract tests where the board provides the corresponding peripheral.

    STM32MP135F-DK has no programmable real-time MCU. Its initial implementation will therefore use the Linux kernel backend. The first class is machine.Pin (modules/linuxmachine/), on the GPIO character device (uAPI v2): lines by kernel name (Pin("PA4")) or (chip, offset), modes IN, OUT, OPEN_DRAIN, pulls PULL_UP, PULL_DOWN, value(), on(), off(), toggle(), init(), deinit(). A line used by the kernel raises OSError(EBUSY); irq() is not provided. tests/hil/t17_mp135_pin.py checks names, errors, inputs with pulls and release without driving any line; tests/hil/t19_mp135_led.py drives the green LD7 and orange LD6 LEDs on the MCP23017 expander (Pin(("mcp23017", 14))), confirmed by eye. tests/hil/t18_mp135_pin_loopback.py checks push-pull and open drain with a jumper across CN8 pins 38 (PA5) and 40 (PA0). A released line keeps its last configuration, as a pin does on the MCU ports when its Pin object is deleted: an output stays an output. Results: docs/log/stm32mp135f-dk-machine-pin.txt. This section records an architectural decision; it does not imply that all of these classes are already implemented.

    Start-up and robustness¶

    The launcher (linux/mpy_launcher.py) checks B1 for safe mode, then, when there is no main.py or in safe mode, shows the ready screen (python/linux/mpy_ready.py): "MicroPython ready", the CDC-ACM port and the TCP address from MPY_REPL_TCP. Any error of the display, and a Ctrl-C from a client connecting at that moment, only costs the ready screen: the REPL starts anyway. The screen writes the kernel uptime at which it was drawn to /run/mpy-ready.

    mpy-repl.service is Type=notify with WatchdogSec=10: the hub pings systemd from its loop, and a hub that stops is restarted. This shows that the REPL is served; a MicroPython program that hangs is not detected, as on the MCU ports, where that is the job of machine.WDT (not implemented yet).

    After a reboot the ready screen is drawn at about 32.7 s of kernel uptime, right after the hub starts. Most of that time passes before sysinit.target (udev, microSD partitions); shortening it means changing the image (phase 9). Results: docs/log/stm32mp135f-dk-phase7.txt.

    Differences from the MCU boards¶

    What LVGL MPY Studio, mpremote and an application see, compared with the MicroPython MCU boards of mpy-lvgl-boards:

    Topic MCU boards STM32MP135F-DK
    sys.platform rp2, esp32, stm32 linux (unix port)
    Filesystem : flash or SD (/, /flash) /usr/local/mpy/fs on the microSD
    Soft reset (Ctrl-D) reinitialises the VM re-executes the process (execve), 0.1–0.2 s; the raw/friendly mode survives
    Hard reset machine.reset() not provided; systemctl restart mpy-repl or a reboot
    REPL channels USB CDC or UART, WebREPL on some CDC-ACM gadget and TCP 192.168.7.1:8266, one process for both
    Ctrl-C the port's keyboard interrupt SIGINT from the pseudo-terminal of the REPL hub
    LVGL service timer callback, scheduled on the main thread thread with the GIL; LVGL event handlers run in it
    Display SPI/RGB/LTDC panel driver DRM dumb buffer, one 480×272 RGB565 buffer, DIRECT mode, no vsync
    machine full port API Pin only (GPIO character device); no irq(), I2C, PWM, WDT yet
    Safe mode board-specific B1 held while the service starts
    Start-up under a second about 33 s of kernel uptime to the ready screen (OpenSTLinux image)

    Known issues¶

    • Start-up is slow (about 33 s to the ready screen) because of the image: udev and the microSD partitions take about 16 s before sysinit.target. A smaller image is phase 9.
    • No vsync or page flip: fast full-screen animations can tear.
    • A MicroPython program that hangs is not detected by the systemd watchdog (it watches the hub); machine.WDT is not implemented.
    • The TCP REPL has no authentication; it listens only on the USB network.
    • mpremote fs cp over the CDC-ACM port is slow (about 17 KiB/s); over TCP it is about 13 times faster.
    • B2 was not tested: its switch on the validation board is damaged.
    • Power loss: /var/log, /var/tmp and /tmp are already in RAM in this image, and install.sh keeps the systemd journal in RAM explicitly (linux/journald-volatile.conf). The root filesystem and /usr/local (its own partition, which holds fs/) are writable ext4: a power cut while the Studio copies an application can still damage it. A read-only root is for phase 9.

    Home screen¶

    install.sh writes a main.py that starts mpy_home (frozen), unless a main.py is already there (MPY_AUTOSTART=none skips it). At power-on the display shows the shell of examples/shell-linux (frozen too), with the keyboard of the serial or TCP terminal: built-in commands, the edit and vi editors in fs/bin, Python programs (name.py in fs/bin, or python file.py) and Linux programs.

    A tap on the terminal opens the app menu: the LVGL MPY Studio apps listed in settings.json, section home ({"apps": [{"name": ..., "path": ".../app_main.py"}]}), Shell, and Power off, which asks first and then runs systemctl poweroff. An app starts in a fresh process (mpyrepl.restart(), a soft reset), so apps never share modules; a small home tab at the top centre brings the shell back the same way. Every soft reset stops the Linux programs the application started with linuxproc.Process (a radio stream does not go on playing).

    LVGL MPY Studio and mpremote take the board as on the MCU ports: Ctrl-A on an empty shell line hands over to the raw REPL, and after a soft reset asked from the raw REPL main.py does not run. Results: docs/log/stm32mp135f-dk-home.txt.
